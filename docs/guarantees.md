# Guarantee ledger

This table records mechanisms and current evidence. "No" does not mean Temporal
is defective; it means the property is outside the cited Temporal guarantee.

| Property | Provided by Temporal | Provided by application | Depends on external system | Evidence |
| --- | --- | --- | --- | --- |
| Workflow state durability | Event History and replay preserve recorded Workflow procedure | Deterministic Workflow code and compatible evolution | Temporal Service persistence/availability | [Captured history replays](../experiments/worker-death/README.md#preserved-milestone-run); incompatible timer change rejected with `TMPRL1100` |
| Activity retry after Worker loss | Server redelivers after timeout according to retry policy | Heartbeats/timeouts must make failure detectable; retry body must be safe | Temporal Service and an available Worker | [Observed after real Worker `SIGKILL`](findings/0001-worker-death-surviving-agent.md); compacted history records started attempt 2 with attempt 1's heartbeat timeout as `last_failure` |
| Stale asynchronous completion by task token | Pinned Server rejects attempt 1's task token after attempt 2 starts | Retain the attempt token and handle `NotFound` without treating it as application reconciliation | Temporal Service version and token integrity | [Rejected in three live trials](findings/0003-activity-id-completion-is-not-attempt-scoped.md); Workflow accepted attempt 2's result |
| Stale asynchronous completion by logical Activity ID | No attempt-owner rejection observed; by-ID request completed the currently pending logical Activity | Authorize an opaque current owner before invoking by-ID completion | Authority store durability and capability secrecy | [Unsafe stale result accepted in three trials; application-fenced arm rejected it](findings/0003-activity-id-completion-is-not-attempt-scoped.md) |
| External exactly-once effect | No | Not claimed generically; application supplies a stable effect ID and the destination-specific protocol | Destination must atomically apply/deduplicate the ID, or expose enough state for bounded reconciliation | [All 18 Go unsafe trials recorded two effects despite one Temporal completion](findings/0004-one-temporal-completion-can-hide-two-effects.md); the [Temporal-native agent loop](findings/0008-temporal-native-agent-loop-recovers-structure-not-effects.md) independently duplicated all three unsafe tool effects while its SQLite-idempotent arms applied one |
| Retry duplicate suppression for idempotent API/database/message | Activity retry only | Stable idempotency, mutation, or message key across attempts | Destination atomically stores the key with the effect/receipt and retains it through retry | [One effect in nine protected trials; two in all nine controls](findings/0004-one-temporal-completion-can-hide-two-effects.md) |
| Sandbox provider operation retry | Activity retry preserves the logical Activity and redelivers it; outer Update identity is separately deduplicated | Derive a stable inner operation key and atomically store the provider effect with its receipt | Provider must retain and return the original instance/snapshot/command/stop receipt | [All 12 unsafe harness trials applied twice; all 12 receipt-keyed arms applied once](findings/0009-sandbox-lifecycle-does-not-close-provider-gaps.md) |
| Sequential retry reconciliation for non-idempotent API/Git | Activity retry only | Query stable correlation/marker before repeating and reject conflicting content | Strongly consistent lookup plus serialized same-ID callers/worktree access | [One effect in six protected trials; two in all six controls](findings/0004-one-temporal-completion-can-hide-two-effects.md); concurrent check-then-act is not covered |
| Stable logical agent identity | No automatic mapping to an external process | Stable session key, owner generation, and durable process/session registry | Store durability plus a trustworthy discovery/routing mechanism | [One session across two attempts](../experiments/worker-death/evidence/milestone1-20260806-v3-reattach/application-state.json); [unregistered child discovered by exact local identity](findings/0005-launch-pending-does-not-identify-process-reality.md), single host only |
| Direct Claude CLI retry after Worker loss | Activity timeout and redelivery only; Temporal neither attaches to the surviving CLI nor reuses its vendor session | Direct relaunch is unsafe; a protected design still needs stable turn identity, start-or-attach or fenced replacement, and destination effect safety | Claude assigns a new session to each direct launch; the destination must deduplicate, fence, or reconcile repeated effects | [All nine authenticated unsafe trials launched two Claude sessions and applied two physical effects while Temporal accepted one outcome](findings/0010-direct-claude-activity-retry-duplicates-turns-and-effects.md); three unfaulted trials launched and applied once |
| No duplicate launch on retry | No | Atomic start-or-attach plus explicit lifecycle and a policy informed by process discovery or fenced replacement | Store serialization; discovery trust; executor registration before effects | [Registered child reattaches](../experiments/worker-death/evidence/milestone1-20260806-v3-reattach/application-state.json); [known-live unregistered child reattaches](../experiments/worker-death/evidence/post-exec-gap-20260806-v3-attach-control-trial-1/application-state.json); [phantom pending launch is replaced](../experiments/worker-death/evidence/launch-gap-20260806-v3-fenced-recovery/application-state.json); `launch_pending` alone cannot choose the policy |
| Liveness after pre-launch Worker death | Activity retry only; Temporal does not know if `exec` happened | Pending-launch detection and fenced conditional replacement | Available Worker, process launcher, and work store | [Blind attach stalls on a phantom](findings/0002-launch-decision-is-not-process-liveness.md); fenced recovery completes in two preserved trials |
| Stale-writer rejection | No | Monotonic attempt check for replacement; generation/token and `running`-state checks at registration and every authoritative mutation | Destination must enforce or delegate the fence | Fenced run events 15–18 reject stale effect/completion; [post-`exec` replacement rejects the old child's exact PID/start registration](../experiments/worker-death/evidence/post-exec-gap-20260806-v3-fenced-replacement-trial-1/application-state.json) |
| Attached sandbox reference authority | No; Workflow routing identity is not a revocable owner capability | Bind commands to the current generation/capability and reject stale authority at the provider or destination | Every workspace mutation path must enforce the fence | [Three unsafe attached references wrote after replacement; all three fenced arms rejected the stale write](findings/0009-sandbox-lifecycle-does-not-close-provider-gaps.md) |
| Stale process cleanup | No | Target the exact session/generation/owner hash and PID/start/group identity; separate revocation, delivery, acknowledgement, and disposition | OS/process reachability and executor cooperation; process-group signaling retains a validation/signal race | [Delayed generation-1 stop leaves generation 2 alive; leader-only negative control leaves its descendant alive](findings/0006-cancellation-requires-application-revocation.md); hostile, uncooperative, cross-host cleanup unresolved |
| Revocation of stale external credentials | No | Issue generation-scoped, revocable authority and stop forwarding stale requests | Every destination must validate or revoke that authority | Work-store capability rejection observed; arbitrary copied API/Git/message credentials are explicitly untested and not claimed |
| Single accepted outcome | Temporal records one Activity completion that it receives | Conditional terminal transition and terminal-state lookup on retry | Store durability | All three arms expose one application outcome; unsafe arm still produced duplicate effects |
| Workflow/Activity cancellation procedure | Workflow cancel and Activity cancel request are durable; `WaitForCancellation=true` waits for the Activity-canceled event observed in the pinned histories | Activity must heartbeat/poll cancellation; disconnected cleanup must be explicit | Temporal Service and an available compatible Worker | [Both wait policies observed across 24 trials](findings/0006-cancellation-requires-application-revocation.md); the [native agent integration](findings/0008-temporal-native-agent-loop-recovers-structure-not-effects.md) ran cleanup after cancellation while its termination control could not |
| Logical agent cancellation | No automatic revocation of a detached process | Atomic terminal cancellation revokes the active generation, blocks replacement, and rejects later registration/progress/effect/outcome | Application-store durability and enforcement at every destination | [All six Temporal-only controls mutated after Workflow cancellation; all 18 application-revoked runs accepted no mutation](findings/0006-cancellation-requires-application-revocation.md) |
| Cancellation reaches exact executor tree | No | Persist exact session/generation/owner/PID/start/group target; signal and acknowledge separately | Linux pidfd/process groups, process reachability/cooperation; stronger containment may require cgroups | [Healthy, Worker-death, and frozen trees stopped under both wait policies](findings/0006-cancellation-requires-application-revocation.md); leader-only negative control left its child alive |
| Artifact durability at post-blob/post-reference failure boundary | History records the Activity result after completion, not the artifact bytes | Content-addressed blob, stable effect reference, atomic publication, and content validation | Filesystem durability and same-filesystem atomic link | [Three protected trials reused one blob/reference; controls created two](findings/0004-one-temporal-completion-can-hide-two-effects.md); blob-written/reference-missing window remains unresolved |
| Sandbox cleanup when create status is unaccepted | Child cancellation and disconnected cleanup are durable only for state the Workflow can name | Reconcile provider resources by stable session/operation identity and record cleanup disposition | Provider must support resource lookup and authoritative stop/delete receipts | [All three parent-close controls left one active instance; all three reconciled arms recorded a stop receipt and left none](findings/0009-sandbox-lifecycle-does-not-close-provider-gaps.md) |
| Sandbox snapshot/fork workspace prefix | Temporal records the accepted snapshot reference and child initialization | Define snapshot lineage and verify restored workspace state independently | Provider snapshot must be immutable/consistent for the declared semantics | [All six forks matched the exact pre-snapshot prefix; unsafe retries also created an unreferenced snapshot](findings/0009-sandbox-lifecycle-does-not-close-provider-gaps.md) |
| Agent event delivery across Continue-As-New | WorkflowStream can carry its log/cursor state to the next run; Temporal retains the run chain | Application must pass stream state and stable session ownership into Continue-As-New and keep the run open long enough to drain terminal items | Consumer polling/retry and any retention after Workflow close remain application/transport concerns | [One controlled continuation](findings/0008-temporal-native-agent-loop-recovers-structure-not-effects.md) preserved the owner capability, approval gate, offsets, and ordered lifecycle events; consumer acknowledgement and closed-run retention are unproven |
| Completed native agent steps during replay | Event History restores completed model/tool Activity results and Workflow decisions | Workflow code and plugin parameters must remain replay-compatible; stable logical identity must not use Activity attempt IDs | Available compatible Worker and destination safety for any retried incomplete Activity | [Model-completion and post-result Worker-death tests plus captured-history replay](findings/0008-temporal-native-agent-loop-recovers-structure-not-effects.md); an incomplete model Activity retried, while completed model/tool Activities were not reissued after `result_built` |
| Duplicate message suppression | Task delivery/retry is durable, not destination deduplication | Stable message ID on every retry | The tested simulated destination atomically retains message-ID deduplication state; real broker semantics are untested | [Three protected trials published one message; three controls published two](findings/0004-one-temporal-completion-can-hide-two-effects.md); broker acknowledgement loss and retention expiry remain unresolved |
| Distinguish wedged application from healthy retry | Temporal exposes task/Workflow state, not external-process truth | Correlate retry attempt, launch lifecycle, PID/process identity, progress, and outcome age | Process registry and clock/telemetry integrity | Launch-gap control records attempt-2 application code attached to `launch_pending` with PID 0; server-visible heartbeat evidence and operator policy for wedged `running` work remain unresolved |
| Cross-system recovery conformance | Workflow/Activity plans export replayable Event History and durably schedule the common procedure | The common harness fixes identities, named barriers, portable policy, append-only evidence, and the independent oracle; PostgreSQL queue/lease logic is application code | PostgreSQL supplies transactions and row locks; destinations still enforce effects and fences | [The publication population](findings/0013-application-policy-equalizes-safety-not-recovery-cost.md) contains 540 valid matched pairs: every unfaulted/protected execution passed all four outcomes and every unsafe control distinguished. All 540 Temporal histories replayed and all 540 PostgreSQL journals were retained. Analysis v5 rehashed 13,503 sealed entries, confined legacy paths to that root, and exactly matched the preregistered schedule and population order. |
| ABA owner-label reacquisition | No automatic application authority fence is claimed | Allocate monotonic generations and opaque capabilities; validate them at every registration, mutation, completion, acknowledgement, and stop boundary | The accepting destination must atomically compare the current generation and capability | In [30 publication pairs per probe](findings/0013-application-policy-equalizes-safety-not-recovery-cost.md), both unsafe systems accepted four obsolete A/g7 actions after A/g9 became current; both fenced systems accepted zero. Protected median recovery was 45.5 ms for Temporal and 1 ms for PostgreSQL on the pinned host; the fence, not the owner label or durability substrate, supplies safety. |
| Bounded recovery dynamics | Durable scheduling alone does not define a shared retry budget, admission limit, poison isolation, or external-agent progress policy | Own and propagate budgets; bound retry/admission concurrency; quarantine poison work; use durable progress deadlines and fenced replacement | Dependency and destination journals must expose physical requests, accepted effects, and exact outage/restoration transitions | Across [30 valid pairs in every recovery stratum](findings/0013-application-policy-equalizes-safety-not-recovery-cost.md), both systems composed with the same bounded policies. Attempt counts, admission decisions, and active dependency time were generally equal; the pinned Temporal arm had higher queue/retry/recovery delay. This is a single-host observation, not a universal product ranking. |
| Direct-Activity versus Child-Workflow topology parity | Not established; Temporal documents both scheduling structures, but this lab has not compared their complete recovery behavior | The frozen design holds identity, work Activity, policy, host envelope, exact barriers, and oracle constant while changing only the extra Child Workflow layer | Hermetic dependency and destination protocols must expose request, effect, receipt, and acknowledgement truth | [Contract](../benchmarks/agent-durability/topology-contract-v1.json) and [preregistration](../benchmarks/agent-durability/topology-preregistration-v1.json) only. Implementation, pilot, and publication are pending, so there is no supported correctness, safety, liveness, diagnosability, or efficiency claim. |

Each completed experiment replaces "pending" with a link to raw evidence, its
finding, exact versions, and the falsifier. Documentation alone never upgrades an
application-level property to observed.
